# java-racingcar-precourse

# 추가 문제 정의

1. 자동차의 수 N을 몇 개로 정의할것인가?
    - 개수가 너무 많으면 출력이 너무 많아짐. 자동차의 수는 최대 10
2. 자동차의 이름 규격 추가 정의
    - 이름에는 공백이 올 수 있으며, 공백으로만 이루어진 이름은 허용되지 않음
    - 사용자의 이름은 알파벳, 숫자만 가능함
3. 시도할 횟수 T의 제한은 몇으로 할 것인가?
    - 시도할 횟수 T도 너무 많으면 출력이 길어짐. 시도할 횟수 T는 20
4. 매 라운드 및 승자의 이름을 출력하는 순서는?
    - 입력으로 들어온 순서를 유지해야 함
5. 자동차가 하나도 없이 빈 문자열이 들어오는 경우는 오류로 간주
6. 시도할 횟수가 0일 때는 정상으로 간주
7. 중복된 이름이 있는 경우는 오류로 간주

## 객체 정의

- **Model**
    - **car**
        - 자동차와 관련된 객체들
        - CarName
            - 인스턴스 : 이름, 최대 길이, 이름 패턴
            - 기능 : 이름에 대한 정보 및 유효성 검사
        - Car
            - 인스턴스 : CarName, 현재 위치
            - 기능 : 이름 조회, 현재 위치, 전진
        - Cars
            - 인스턴스 : List<Car>
            - 기능 : 자동차 전진 여부 결정, 자동차 전진 수행, 우승자 계산
    - **strategy**
        - 전진 전략과 관련된 객체들
        - MoveStrategy
            - 기능 : 전진 여부를 결정하는 전략 인터페이스
        - ThresholdMoveStrategy
            - 인스턴스 : 정수 공급자, 임계값
            - 기능 : 정수 공급자에서 획득한 정수를 기반으로 임계값에 따라 전진 여부 결정
    - **provider**
        - 정수 공급자와 관련된 객체들
        - NumberProvider
            - 기능 : 정수를 제공하는 인터페이스
        - RandomNumberProvider
            - 기능 : 0에서 9 사이의 랜덤 정수를 제공
        - SequenceNumberProvider
            - 인스턴스 : 정수 리스트
            - 기능 : 리스트에 정의된 정수를 순차적으로 제공
- **Service**
    - RaceService
        - 인스턴스 : MoveStrategy
        - 기능 : Cars의 일괄 전진을 수행. 수행 후 결과를 반환. 우승자 계산
    - ParseService
        - 기능 : 입력된 자동차 이름 문자열을 파싱하여 List<String> 으로 반환
- **Controller**
    - RaceController
        - 인스턴스 : RaceService, RaceView
        - 기능 : 입력과 서비스 로직 제어, 시도 횟수만큼 라운드 실행 요청 및 결과 출력 요청, 최종 우승자 출력 요청
- **View**
    - RaceView
        - 인스턴스 : InputHandler, OutputHandler
        - 기능 : 입출력 수행

# 주요 의사 결정 흐름, 학습 내용, 느낀점
개발을 진행하면서 어떠한 생각을 하면서 개발을 해왔는지, 그리고 코드를 작성했을때의 근거를 정리한 내용입니다.
**제 생각에 대한 틀린 점이나 피드백 주시면 정말 감사하겠습니다!**

1. 유효성 검사의 위치 결정
- 계기 : 자동차 이름의 유효성을 검사하는 위치를 어디에 작성해야 좋을지
- 개발 과정
    - 생성자 내부에서 수행 -> 복잡한 검증 로직이 포함되는 경우 생성자에서 수행하는 작업이 너무 많아졌음 -> 팩토리 메소드에서 정규화 및 검증을 수행하자
    - 팩토리 메서드가 조립과 유효성 검증을 하는것이 맞는가 -> 팩토리는 조합만, 유효한 객체 생성은 생성자에서만 하도록 다시 리펙토링
    - 자동차 객체가 이름에 대한 자세한 조건들(이름의 길이, 정규식 등)을 모르는게 더 객체지향적인 것 같다 -> 자동차 이름이라는 ValueObject로 분리하고, 자기 스스로 검증하도록 수정하자
- 학습 내용 : DTO와 VO에 대한 차이를 공부, 팩토리 메서드와 생성자의 책임에 대해 다시 생각

2. 자동차의 이동 범위 결정
- 계기 : 확장성을 고려하여 자동차가 항상 한 칸만 전진하는 것이 아닌 여러 칸을 전진할 수 있도록 확장할지 고민
- 개발 과정
    - 한 칸씩 이동하도록 구현 -> 확장성에 대한 고민
    - 여러 칸 이동 구현 -> 이동 범위에 대한 예외 추가 및 여러 로직 추가로 인한 복잡도 증가
    - 소프트웨어 개발 3대 원칙 학습, YAGNI 원칙에 따라 필요한 만큼만 구현
- 학습 내용 : 소프트웨어 개발 3대 원칙

3. 테스트 코드 작성 시 give-when-then 구분
- 계기 : 기존에는 테스트 구조를 구분하지 않고 작성하여 가독성이 떨어졌음
- 학습 내용 : 테스트 코드 작성 시 give-when-then 패턴이 있다는 것을 학습하였고, 이를 적용하여 테스트 코드를 작성

4. MVC vs DDD
- 계기 : 개발을 진행하다 보니 기존처럼 model 폴더 하나로만 구성하기에는 자동차, 이동 전략, 정수 공급자 등 객체들이 너무 많아짐
- 개발 과정
    - MVC 패턴으로 시작하여 개발 진행 -> 초기 설계와는 달리 IntProvider, MoveStrategy 등 여러 객체가 추가되었음
    - MVC 패턴을 적용하기에는 너무 많은 model 객체로 인해 구분이 필요해졌음
    - DDD를 적용하기에는 각 도메인 별 비즈니스 로직이 존재하는것이 아님
    - MVC 패턴에서 model만 도메인별로 구분함
- 학습 내용 : MVC, DDD

5. 랜덤을 고려한 테스트 코드 작성 방법, 이동 전략 객체와 정수 공급 객체의 분리
- 계기 : TDD 진행 중, 실행 할 때마다 달라지는 랜덤함수로 인한 테스트 코드 작성에 어려움을 겪음
- 개발 과정
    - 랜덤 테스트를 위한 방법 필요성 -> 이동 결정 객체를 시퀀스 기반과 랜덤 기반으로 분리하여 개발 진행
    - 시퀀스 기반에서 대부분의 테스트를 수행하고, 랜덤 기반에서는 간소화된 테스트를 수행
    - 이동 결정 객체에서 담당하는 동작이 많아짐 (난수 생성, 이동 결정) -> 분리 필요성을 느낌
    - 이동 결정은 이동 전략이라는 객체로 분리하여, '임계점 기반 이동전략'이라는 개념으로
    - 결정하기 위한 정수를 만들어주는 기능은 정수 공급자라는 객체로 분리하여, '랜덤 기반 정수 공급자'와 '시퀀스 기반 정수 공급자'라는 개념으로 분리
    - 이동 전략은 임계점 기반 이동 전략으로, 테스트 할 때는 시퀀스 정수 공급자 / 실행에는 랜덤 정수 공급자를 사용함으로써 테스트 및 실행 용이성 확보
    - 의존성 주입이 필요한 이유를 확실히 알게 되었음
- 학습 내용 : 의존성 주입, 책임 분리, 랜덤 함수에 대한 결정적 테스트 방법 경험, 실행 / 테스트 이원화

6. 자동차 이동의 책임 주체 결정
- 계기 : 개발 완료 후 리펙토링 도중, Cars가 자동차들의 이동을 결정하는 로직을 확인한 후 의아함을 느낌
- 개발 과정
    - 초기에는 Cars에서 for문을 돌며 이동 전략 활성화 일 때만 자동차를 전진 시킴 -> 자동차가 운전을 해서 가는것이 아니라, 사람이 자동차 모형들을 손으로 움직이는 느낌이 들었음
    - 이동 책임을 Cars에서 Car로 이관
- 추가 의문 : 이동 전략을 RaceService -> Cars -> Car로 전달하는것이 맞는지
    - 개별 자동차들이 각각의 이동 전략을 가지고 있는 것이 더 자연스러운지, 그리고 많은 과정을 거쳐 전달하는게 맞을지에 대한 의문이 듬
    - 현 요구사항에서는 자동차마다 이동 전략을 가질 수 있는것이 아니라 경기 규칙이기 때문에 현 구조를 유지하는 것으로 결정
    - 향후 요구사항 변경 시, Car 객체 생성에서 이동 전략을 주입함으로써 자동차들이 다양한 이동 전략을 가지도록 리펙토링 가능성을 생각해보았음

7. 테스트 커버리지 학습 및 적용
- 계기 : 1주차 미션 후 스터디에서 테스트 커버리지라는 것을 새로 접함
- 기존에는 커버리지 테스트 없이 예외처리를 구현하다보니 지난주차에서는 과도하게 쓸데없는 예외를 많이 처리
- 이번 주차에서는 테스트 커버리지를 활용하여 불필요한 코드 분기 및 예외 처리를 제거하였고, 테스트 커버리지를 100% 달성
- 테스트 커버리지를 항상 100%로 채워야 된다는것이 아니고, 이를 맹신하면 안된다는 것을 인지
- 이번에 처음 적용하다보니 뭔지 잘 모르고 적용하다보니 추가 학습에 대한 필요성을 느낌
